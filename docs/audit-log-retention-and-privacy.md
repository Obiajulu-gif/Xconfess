# Audit log retention and privacy expectations

Audit logs are security records. They should help admins understand privileged or sensitive actions without exposing confession content, private wallet material, or unnecessary personal data.

## Current implementation references

- Service: [`xconfess-backend/src/audit-log/audit-log.service.ts`](../xconfess-backend/src/audit-log/audit-log.service.ts)
- Entity: [`xconfess-backend/src/audit-log/audit-log.entity.ts`](../xconfess-backend/src/audit-log/audit-log.entity.ts)
- Tests should live beside the audit-log module when added, for example `xconfess-backend/src/audit-log/audit-log.service.spec.ts`.

## Safe fields to retain

Audit records may retain:

- Action type, actor type, actor id, and admin/user id where applicable.
- Entity type and stable entity id, such as report id, comment id, confession id, export id, request id, or transaction id.
- Timestamps generated by the server.
- Request correlation ids and high-level source labels.
- Admin decision metadata, such as previous status, new status, moderation reason category, or rollout state.
- Truncated wallet addresses or transaction hashes when they are needed to investigate public-chain actions.

## Fields to redact or avoid

Audit records must not retain:

- Private keys, secret phrases, recovery phrases, seed material, or signing payload secrets.
- Full confession body text unless a future legal/compliance requirement explicitly documents the exception.
- Raw message content, private replies, or encrypted plaintext.
- Authentication tokens, password hashes, reset tokens, email verification tokens, session cookies, or bearer tokens.
- Full request/response bodies from user-generated endpoints.
- Unbounded user-agent or IP enrichment data beyond what the existing audit entity stores.
- Real user data in docs, fixtures, screenshots, or examples.

## Admin visibility expectations

Admin-facing audit views should expose only the fields required to answer who did what, to which entity, and when. Prefer entity ids and status transitions over raw user content. When wallet data is shown, display a shortened address or transaction hash with a link to the relevant public explorer where appropriate.

## Retention and cleanup assumptions

The repository does not currently define a hard retention window in the audit-log service. Until a cleanup job is implemented, treat audit logs as long-lived operational security records and keep the stored data minimal. If a retention policy is added later, it should document:

- Default retention period.
- Whether admin/security actions have a longer retention period than routine user actions.
- Cleanup cadence and whether records are deleted, archived, or anonymized.
- Any legal hold or incident-response exceptions.

## Review checklist

Before adding a new audit event, confirm that:

1. The action type is specific enough for investigation.
2. Metadata contains ids and status values, not private content.
3. Any wallet address or transaction hash is necessary and preferably shortened in admin UI.
4. No private key, secret phrase, auth token, or raw sensitive payload is logged.
5. Tests or future tests assert both the positive event and that forbidden fields are not persisted.
